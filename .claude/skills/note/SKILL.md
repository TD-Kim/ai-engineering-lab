# /note — 학습 노트 정리

사용자가 커밋하기 전에, 지금 대화에서 오간 **개념 설명·힌트·확인한 결과**를 학습 노트로 남긴다.
저장소 CLAUDE.md의 규칙(정답 코드는 요청 시만, 파일 임의 수정 금지, 지어내지 않기)을 그대로 따른다.

## 인자

- 인자 없음 또는 주제만 (`/note`, `/note 시스템 프롬프트`): 아래 **A. 노트 쓰기**
- `메모`로 시작 (`/note 메모`): 아래 **B. 타임라인 메모 채우기**

## A. 노트 쓰기

1. **모으기.** 이 대화에서(이미 노트로 정리한 부분 이후만) 다음을 모은다.
   - Claude가 설명한 개념, 사용자가 질문한 것
   - 사용자가 실제로 실행해서 확인한 결과(명령, 출력, 숫자)
   - 막힌 점과 원인, 다음에 할 일
   - 지금 힌트가 몇 단계까지 나갔는지(CLAUDE.md §3)
   주제를 인자로 받았으면 그 주제와 관련된 것만 모은다.
2. **지어내지 않는다.** 대화에 없는 설명을 새로 덧붙이지 않는다. 실행하지 않은 결과·숫자는 쓰지 않고, 확인하지 못한 것은 "미확인"으로 적는다.
   정답 코드는 대화에서 사용자에게 실제로 보여 준 경우에만 옮긴다. 힌트만 준 문제는 힌트까지만 적는다.
3. **파일.** `docs/notes/<오늘 날짜(한국 시각) YYYY-MM-DD>.md`
   - 없으면 새로 만들고, 첫 줄은 `# 학습 노트 — YYYY-MM-DD`
   - 있으면 맨 아래에 새 절을 덧붙인다. 이미 적힌 내용은 고치지 않는다.
4. **양식.** 절마다 아래 모양으로 쓴다. 없는 칸은 뺀다. 처음 배우는 사람이 다시 읽어도 이해되게, 용어는 풀어 쓰고 작은 숫자 예시를 남긴다.

   ```markdown
   ## HH:MM — <주제>

   > 최종 서비스에서의 위치: <사용자 → Spring Boot → Python AI 서버 → RAG/GraphRAG → 벡터DB/Neo4j → LLM 중 어디인지 한 줄>

   ### <개념 이름>
   - 개념: 무엇인지
   - WHY: 왜 필요한지
   - 서비스 관점: 비용·지연·품질에서 무엇을 판단해야 하는지
   - 예시: 손으로 따라 할 수 있는 작은 숫자나 짧은 입력·출력
   - 관련 코드: `경로:줄`

   ### 해 보고 확인한 것
   - <실행한 것> → <실제로 나온 결과>

   ### 막힌 점
   - <무엇이, 왜>

   ### 다음 할 일
   - <다음 단계>, 힌트 진행: <N>단계까지 받음

   ### 미확인
   - <확인이 필요한 것>
   ```

5. **보여 주기.** 덧붙인 내용을 그대로 사용자에게 보여 주고, 고칠 곳이 있는지 묻는다.
6. **커밋은 하지 않는다.** 사용자가 직접 커밋한다. 무엇을 만들었는지 드러나는 커밋 메시지를 한 줄 제안하고,
   커밋 뒤 `/note 메모`로 타임라인 메모 칸을 채울 수 있다고 알린다.
7. 노트 파일 말고 다른 파일은 고치지 않는다.

## B. 타임라인 메모 채우기 (`/note 메모`)

1. `docs/TIMELINE.md`에서 **가장 최근 커밋의 항목**을 찾는다(`git log -1 --format=%s`의 제목과 항목 제목이 같은지 확인).
   찾지 못했거나 메모 칸이 이미 차 있으면 고치지 말고 사용자에게 알린다.
2. 그 항목의 `- 메모: ` 줄**만** 바꾼다. 자동 기록 부분(시각, 파일, 함수)은 건드리지 않는다.
   내용: 배운 것·막힌 점·다음 할 일을 한두 문장으로, 끝에 오늘 노트 링크 `(노트: docs/notes/YYYY-MM-DD.md)`.
   오늘 노트가 없으면 이 대화의 내용으로만 짧게 쓴다.
3. 바꾼 줄을 보여 준다. 커밋은 사용자가 한다(타임라인만 바뀐 커밋은 훅이 새 항목을 만들지 않는다).
